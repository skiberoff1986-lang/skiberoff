# Подключение будущего Windows-клиента

Веб-сервер предоставляет JSON API. Текущий локальный EXE этим API не пользуется; его адаптация — отдельный этап. Клиент должен хранить ID неподтверждённой команды до получения окончательного результата. Изменять PostgreSQL напрямую из Windows-клиента не следует.

## Сеанс

1. `GET /api/session` — получить CSRF-токен и сохранить cookies.
2. `POST /api/login` с `{ "login": "...", "password": "..." }`, прежними cookies и заголовком `X-CSRF-TOKEN`.
3. Снова `GET /api/session` — получить токен, привязанный к вошедшему пользователю. Ответ содержит права и часовой пояс.
4. При `mustChangePassword=true` вызвать `POST /api/password` с `oldPassword`, `newPassword`, затем снова получить session.
5. Все изменяющие запросы передают CSRF-токен и cookies. Пароль и токен MAX не передаются в командах журнала.

В production используется HTTPS; cookies HttpOnly, Secure, SameSite. Windows-клиенту нужен собственный `CookieContainer`. Публичной регистрации, CORS для посторонних сайтов и постоянного административного API-ключа нет.

## Основные запросы

| Запрос | Содержание |
|---|---|
| `GET /api/shops` | Доступные цеха |
| `GET /api/records?shop=01&state=open&page=1` | Страница 40 записей и итог по всему фильтру |
| `GET /api/records/{id}` | Запись, версия, история, вложения, очередь |
| `POST /api/records` | Регистрация |
| `POST /api/records/{id}/commands` | Новый этап или изменение СДУ |
| `GET /api/records/export` | CSV; поддерживает те же фильтры |

Дополнительные фильтры: `search`, `from`, `through` (даты регистрации, `yyyy-MM-dd`, конечная включительно). `state` — `open` / `closed`.

Создание:

```json
{"commandId":"уникальный UUID","shop":"01","crane":"04А","fault":"Описание","eventAt":null}
```

Этап:

```json
{"commandId":"уникальный UUID","expectedRevision":1,"kind":"Responded","eventAt":null,"responsible":null,"shiftMaster":"Петров П.П.","workDescription":null,"worksWithRestrictions":null}
```

`kind`: `Responded`, `RepairStarted`, `Restored`, `AccountingChanged`. Для `Restored` требуется `workDescription`. Для `AccountingChanged` — логический `worksWithRestrictions`. `eventAt` — `yyyy-MM-ddTHH:mm` по часовому поясу предприятия; `null` означает текущее время сервера в этом поясе. Серверное время принятия и автор не принимаются от клиента.

Успех изменения: `{ "id": "...", "revision": 2, "data": { ... } }`. После него запрашивайте карточку снова — она могла уже дополниться действиями коллеги. Повтор того же `commandId` с тем же содержимым возвращает исходный результат, даже если текущая версия уже выше. Это семантически тот же JSON, порядок полей значения не имеет.

`409` — конфликт этапа / версии / повторного идентификатора с иным содержимым; обновите карточку. `401` — требуется вход; `403` — недостаточно прав / требуется смена временного пароля; `400` — ошибка данных или CSRF; `413` — превышен размер / квота. При потерянном ответе, `408` или `5xx` повторяется исходная команда с исходным ID, а не новая.

## Вложения

1. `POST /api/records/{id}/media`: `commandId`, `name`, `size`, `notifyMax=true`, необязательная `expectedSha256`. Ответ: ID загрузки и `chunkSize`.
2. `GET /api/uploads/{id}` — состояние и номера сохранённых частей. Доступен добавившему файл сотруднику.
3. `PUT /api/uploads/{id}/chunks/{index}` — двоичная часть, `Content-Type: application/octet-stream`, CSRF и cookies. Размер — `chunkSize`, кроме последней. Нумерация с нуля. Повтор идентичной части безопасен, другая часть с тем же номером отклоняется.
4. `POST /api/uploads/{id}/complete` с отдельным стабильным `commandId` — проверка, фиксация и постановка в очередь MAX. До этого файл не отображается среди зарегистрированных вложений.
5. `GET /api/media/{id}/file` — скачивание только при доступе к цеху.
6. `POST /api/media/{id}/queue` с `commandId` — поставить сохранённый файл в очередь, если он ещё не ставился. Повторная пересылка уже отправленного файла таким запросом не создаётся.

`notifyMax=false` разрешён только администратору для переноса. Контрольная сумма вычисляется сервером. Дедупликация действует по SHA-256 внутри одной заявки. Отменённая или неопределённая отправка регулируется через администраторский раздел MAX.
