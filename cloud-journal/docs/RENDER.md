## Перед публикацией

1. Загрузите подготовленный пакет в подтверждённый репозиторий: `cloud-journal`, `.github/workflows/cloud-journal.yml` и корневой `render.yaml`. `.env`, локальный журнал, фото и токен бота в репозиторий не добавляются.
2. Дождитесь успешного GitHub Actions workflow `Cloud journal checks`, включая тесты с PostgreSQL и HTTP и сборку Docker-образа. Альтернатива — выполните `docker compose --profile checks run --build --rm checks` на своём компьютере. Текущая среда подготовки эти тесты не выполнила.
3. В [панели Render](https://dashboard.render.com/) выберите подтверждённое рабочее пространство, затем **New → Blueprint**, подключите репозиторий и укажите корневой файл `render.yaml`. В конфигурациях, находящихся внутри `cloud-journal`, пути рассчитаны на отдельный репозиторий с проектом в его корне; для текущей структуры используется внешняя копия с исправленными путями.
4. Перед применением проверьте имена ресурсов, регион и итоговую стоимость. Если такие имена уже заняты другим проектом, переименуйте обе ссылки на БД согласованно. Не применяйте конфигурацию к чужому сервису.

## Выбор конфигурации

| Файл | Назначение | Ресурсы |
|---|---|---|
| `render.yaml` | Демонстрация на тестовых данных | Бесплатный web + бесплатная PostgreSQL; лимит вложений 500 МБ |
| `render.production.yaml` | Пример постоянного размещения, требует оплаты | Web `0.5c-512mb`, PostgreSQL `0.5c-1g`, диск 15 ГБ; квота вложений 5 ГБ |

Бесплатный веб-сервис засыпает после 15 минут без входящих запросов. На время сна обработка очереди MAX приостанавливается. Бесплатная PostgreSQL истекает через 30 дней, не имеет управляемых резервных копий и ограничена 1 ГБ. Поэтому бесплатный файл не предназначен для хранения единственного рабочего журнала. Для постоянной эксплуатации выберите подходящий платный план и резервное копирование. Стоимость проверьте в панели перед созданием ресурсов; платная конфигурация сама ничего не оплачивает.

Оба сервиса располагаются во Frankfurt; база подключается по внутренней сети, внешние подключения к ней закрыты. Регион выбран как пример близкого к европейской части России варианта. До рабочего переноса проверьте доступность сайта с телефона сотрудников.

## Первый вход

После успешной сборки откройте адрес сервиса `https://…onrender.com`. Render подставляет `RENDER_EXTERNAL_URL`, приложение использует его как допустимый адрес. Health check: `/healthz`.

В Environment сервиса найдите сгенерированный `BOOTSTRAP_PASSWORD`. Логин — `admin`. Войдите и смените пароль; затем создайте личные записи сотрудников и назначьте цеха. Для смены пароля впоследствии используется сайт, а не переменная `BOOTSTRAP_PASSWORD`: она применяется только при создании первого администратора в пустой БД. После первоначальной настройки её можно удалить из Environment.

Откройте ссылку с телефона через мобильный интернет и проверьте вход. Добавить ярлык: в меню Chrome / Safari выберите добавление на главный экран. Интернет для записи обязателен; автономной синхронизации нет.

## Подключение MAX

Сначала перенесите журнал и убедитесь, что данные правильные. Затем в **Environment** веб-сервиса добавьте:

| Переменная | Значение |
|---|---|
| `MAX_BOT_TOKEN` | Токен существующего бота из кабинета MAX, без слова Bearer и пробелов |
| `MAX_CHAT_ID` | Точный числовой ID общей группы, в которой состоит бот |

Значения вводятся непосредственно в Render; не публикуйте их в чате или коде. Зашифрованные настройки старой Windows-программы в облако не переносятся.

Сохраните Environment с перезапуском сервиса. Войдите администратором в раздел MAX: должна появиться успешная проверка доступа к группе. Следующее реальное событие или загрузка медиа попадёт в очередь. Уведомления для старых этапов автоматически не создаются. Ранее добавленные фото / видео можно отправить кнопкой «В MAX» в карточке.

Уже созданное уведомление сохраняет исходный ID группы. При смене `MAX_CHAT_ID` старая очередь не перенаправляется автоматически: проверьте её и при необходимости отмените старые отправки.

При неверном токене, ID или отсутствии прав исправьте параметры. Если сообщение имеет состояние «Нужно проверить группу», проверьте чат перед ручным повтором. Не отключайте проверку TLS для устранения проблем соединения.

## Настройки и обновления

- `DATABASE_URL` берётся из связи `fromDatabase`; вручную в браузер он не передаётся.
- `BUSINESS_TIMEZONE=Europe/Moscow` задаёт время предприятия.
- `MEDIA_QUOTA_BYTES` ограничивает суммарный объём файлов, включая незавершённые загрузки. Размер БД дополнительно включает индексы, историю, журнал транзакций и служебные данные; следите за фактическим заполнением.
- `RENDER_TLS_TERMINATION=true` разрешено только внутри Render (`RENDER=true`). Не копируйте его на иной хостинг. Для своего reverse proxy используйте HTTPS и явно заданные доверенные сети `TRUSTED_PROXY_NETWORKS`.
- Для собственного домена задайте корневой `PUBLIC_URL=https://ваш-домен` и настройте домен с TLS в Render. После этого приложение принимает этот адрес как основной.
- Автодеплой намеренно выключен: после изменений сначала проверки и резервная копия, затем ручной Deploy подходящего коммита. Приложение не удаляет и не пересоздаёт рабочую БД при запуске. Будущие изменения схемы требуют отдельной миграции.
